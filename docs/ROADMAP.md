## 단계별 메모

- **②**
  - 샘플은 7.2 메시지 형식 그대로다.
  - 접전 역전승, 연장 끝내기, 일방적 경기 3종이다.
  - 필드 설명은 `docs/API.md`에 있다.
- **③**
  - CORS 허용 도메인은 서버의 `CORS_ORIGINS`로 정한다.
  - 리플레이 WebSocket은 `pause`/`resume`/`seek`/`speed` 명령을 받는다.
  - `wp_home`은 반올림 전 실수다. 그래프와 로그 오즈 눈금에 쓴다.
- **③-b**
  - 절차는 아래 "③-b 아키텍처 이해 점검 (Archify)" 절에 있다. 지금은 실행하지 않는다.
- **④**
  - 서버는 한 프로세스로 뜨고, 재계산 워커는 같은 컨테이너에서 fork된다.
  - 실시간 모드는 메모리 약 3GB가 필요하다(시즌 모델 약 2GB + 워커).
  - 리플레이 전용 모드(`FEED_SOURCE=off`)는 모델을 적재하지 않아 가볍다.
  - 공개 배포 전에 MLB 데이터 이용 조건을 확인해야 한다(`reports/realtime_report.md`의 "확인 필요 사항").
- **⑤**
  - 지금은 구조화된 JSON 경고 로그로만 남는다.
  - `SENTRY_DSN`을 설정하고 `sentry-sdk`를 설치하면 경고 이상이 Sentry로 간다.

## ③-b 아키텍처 이해 점검 (Archify)

**목적**: 배포 전에, 내가 직접 이 서비스의 구조를 설명할 수 있는 상태가 되는 것. 그림을 받는 것이 목적이 아니라, 그림의 화살표를 코드와 하나씩 대조하며 이해하는 것이 목적이다.

### 시작 조건
- ③ 사이트 본 개발이 끝나서 **로컬에서 실시간 모드와 리플레이 모드가 모두 처음부터 끝까지 동작**한다.
- ④ 배포 전이다. 배포 설정(Railway, Vercel)을 넣기 전의 구조를 먼저 이해하고, 배포 뒤에 다시 그려 비교한다.

### 준비
1. **스킬 내용 확인**: Archify(`tt-a1i/archify`, MIT)의 `SKILL.md`를 먼저 읽고, 에이전트에게 무엇을 시키는지 확인한다. 이상한 지시(외부 전송, 권한 요청 등)가 있으면 쓰지 않는다.
2. **버전 고정**: 확인한 시점의 커밋 해시를 이 문서에 적고, 그 버전으로 설치한다.
3. **설치 범위**: 전역 설치(`-g`) 대신 이 저장소 작업 세션에서만 쓴다. Node.js 18 이상이 필요하다(`node -v`로 확인).
4. **점검**: `doctor`와 `demo`로 동작을 먼저 확인한다.

### 그릴 그림 (질문 하나에 그림 하나, 노드 8–12개, "이 저장소에 실제로 있는 것만")
| # | 질문 | 종류 |
|---|---|---|
| 1 | 라이브 피드가 들어와서 웹 화면에 WP가 뜰 때까지 어떤 모듈을 지나는가? | 아키텍처 |
| 2 | 투구 하나가 도착해서 웹의 WP 바가 바뀌기까지 무슨 일이 순서대로 일어나는가? | 시퀀스 |
| 3 | 투수 교체나 대타가 나오면 재계산은 어떻게 돌고, 그동안 B2E 값은 어떻게 표시되는가? | 시퀀스 |
| 4 | Retrosheet 원본이 어떤 단계를 거쳐 `models/`의 테이블과 능력치가 되는가? | 데이터플로 |
| 5 | 피드의 중복·정정·역행 스냅샷은 어디서 걸러지고 어떻게 기록되는가? | 데이터플로 |

| 7 | 웹 프론트엔드는 어떤 API와 WebSocket을 어떤 순서로 부르는가? | 시퀀스 |

### 이해 확인 방법
- 그림마다 화살표를 하나씩 소스 링크로 따라가며 "이 함수가 정말 저것을 부르는가?"를 확인한다.
- 그림과 `docs/REALTIME.md`, `docs/API.md`, `docs/HANDOFF.md`가 다르면 목록으로 남긴다. 문서가 틀렸으면 문서를, 코드가 의도와 다르면 이슈를 만든다.
- 마지막으로 그림 1과 2를 보지 않고 직접 설명해 본다. 막히는 부분을 다시 질문한다.

### 산출물
- `docs/architecture/` 아래 그림별 HTML 파일과, 각 그림에서 확인한 점·발견한 차이를 적은 `docs/architecture/NOTES.md`
- Archify 결과는 GitHub README 안에서 보이지 않으므로, 그림 1과 2는 **Mermaid 정적 버전**도 만들어 README에 넣는다.

### 이후
- ④ 배포 뒤에 그림 1을 다시 그려 배포 전과 비교한다(Railway 서버, Vercel 웹, 환경 변수가 어디에 들어갔는지).
- 큰 기능을 추가할 때마다 해당 그림만 다시 그려 전후를 비교한다. 저장소 전체를 반복해서 그리지 않는다(토큰 소모가 크다).

### 대안
- Archify를 쓸 수 없거나 `SKILL.md` 확인에서 문제가 보이면, 같은 질문 목록으로 Claude Code에게 Mermaid 다이어그램을 그리게 한다. 이 환경에는 Mermaid CLI(`mmdc`)가 설치되어 있다. 검증 단계는 위의 "이해 확인 방법"으로 직접 한다.

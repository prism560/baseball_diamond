# 실시간 호출 순서 (B3)

B3는 하나의 DP 엔진으로 경기 전 WP와 경기 중 WP를 일관되게 계산한다. 실시간 서비스는 아래 순서로 호출한다. 시간은 이 저장소의 4코어 클라우드 컨테이너에서 단일 스레드로 측정한 값이며, `reports/b3_report.md`에 실측치가 있다.

## 1. 경기 전 (라인업 발표 후 1회)

1. `wp.b3_game.build_context(S, ...)`로 시즌 문맥을 만든다. 하루에 한 번이면 충분하다. 문맥에는 능력치 저장소, 구장·플래툰 표, 리그 전이(K=10 고정), 해저드, 불펜 등급이 들어 있다.
2. `game_inputs(ctx, game, lineups, starters, Ablation())`를 호출한다.
   - 선발 라인업 9명과 양 팀 선발 투수를 넣는다.
   - 능력치는 모두 경기 전날까지의 정보로 계산된다.
3. `Engine(R=20, float32).solve(gi)`로 전체 상태의 WP 배열을 만든다. 경기당 약 6–10초 걸린다.
4. 경기 전 WP는 `res.wp(1, 0, 0, 0, 0, composite(0, 0), composite(0, 0))`이다.

## 2. 투구마다 (조회만)

1. 현재 상태를 조회한다: 이닝, 초/말, 아웃, 주자, 점수차, 공격 팀 합성 상태 `composite(타순, 단계)`, 수비 팀 합성 상태.
   - 단계: 상대 선발이 등판 중이면 타순 바퀴−1(0, 1, 2), 불펜이면 3이다.
2. 타석의 첫 투구 전에 한 번 다음을 계산한다.
   - 그 타석의 매치업 q를 구하고, `count_chain.fit(base, q)`로 IPF를 맞춘다(1ms 미만).
   - `b3_game.after_outcome_G(...)`로 결과별 이후 값 G를 구한다.
3. 투구마다 WP = `P(o | 현재 카운트) · G`. 0-0에서는 DP 값과 일치한다(테스트로 확인).
4. **타석 도중 도루·폭투 등으로 주자 상태가 바뀌면** 바뀐 상태로 2번을 다시 계산한다.
   - B2/B3는 타석 중 주자 이벤트를 결과별 진루 테이블에 흡수해 두었다. 따라서 이벤트가 이미 일어났다면 실제 상태로 다시 조회하는 것이 맞다.

## 3. 교체가 일어났을 때 (재계산)

| 사건 | 처리 | 측정 비용 |
|---|---|---|
| 투수 교체 | `solve(gi, override={(이닝, 초말): (투수 능력치, 투구 손)}, upto=현재 하프, cache=직전 결과, start=현재 하프)`. 그 투수의 능력치를 현재 하프이닝 끝까지 쓰고, 이후는 불펜 혼합 분포를 쓴다. 다음 하프이닝이 시작될 때 같은 투수가 계속 던지면 그 하프로 다시 부른다. | 하프 1개, 약 0.3–0.5초 |
| 대타·대주자(타순 변경) | 라인업을 갱신하고 `solve(gi, start=현재 하프)`를 호출한다. 남은 하프이닝 전체를 다시 푼다. 대타 투입 확률은 모델링하지 않고, 실제로 일어난 교체만 반영한다. | 남은 하프 수에 비례, 최대 약 7초 |
| 투구 수 정보(선택) | `Hazard.prob(..., pitch_count_adj=로그오즈 보정)`. 투구 수는 DP 상태에 없고 해저드 보정 입력으로만 쓴다. | 커널 재구성, 선발 등판 중인 하프만 |

## 4. 화면 표시

`round(100 * WP)`를 홈 승률로 쓰고, 원정 승률은 그 나머지다. 이렇게 하면 합이 항상 100이다(`wp_b2.PitchWP.split` 참고).
